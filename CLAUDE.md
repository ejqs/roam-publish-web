# Branch workflow

Never commit straight to `main`. For every change: push to `develop` first, wait for the Railway `staging` environment (shadow database, project `roam-publish`) to deploy it successfully. Its pre-deploy step runs the tests against the shadow DB, so a SUCCESS deploy means they passed. Never open the PR if the staging deploy failed, then open a PR from `develop` into `main`. Repeat for each later change.

# Changelog

`CHANGELOG.md` is what users see at `/updates` (What's new); nothing there is generated from commits. Every change users would notice adds a bullet in the same commit: under the next release's `## x.y.z (YYYY-MM-DD)` (a [semantic version](https://semver.org), dated the day it reaches `main`), then a `### Area` (reuse one: Dashboard, Published pages, Publishing, Discover, Security, Site…). Start each bullet with its kind: `Breaking:` (something that worked stops working as before, or needs people to act, like updating the extension; say what to do), `New:` (something you couldn't do before), `Improved:` (works better or reads clearer) or `Fixed:` (was broken); a test fails a bullet without one. Each PR into `main` is one release: if `main` already has the top version, add a new heading above it, bumping the minor version when the release has a `New:` change, the patch when it has only `Improved:` and `Fixed:`, and the major only when the release removes or changes something older extensions rely on (an `/api/ext` field or route), which gets a `Breaking:` bullet (a test requires a major bump for one; see Extension compatibility), and set `package.json`'s `version` to match. Tests and the Changelog check enforce all of this. /updates stamps each entry with when the deploy carrying it first started, so it says exactly what a reader missed. Rewording a bullet that already shipped is fine: /updates keeps it at its release's time (lib/whats-new.ts `stamp`), so to announce something again, add it under the new version instead. Write for the people who use the site, one change per bullet, wrapped lines indented. Leave out tests, refactors, internal tooling and fixes too small to notice. The Changelog check fails a PR into `main` that changes `src/`, `public/` or `drizzle/` without touching `CHANGELOG.md`; label it `no-changelog` when there's genuinely nothing to log.

# Where code lives

`src/app/` holds routes: pages, layouts, route handlers and the UI only those routes use. Server actions (`"use server"`) live in `src/server/actions/`, one file per feature; shared logic and data access live in `src/lib/` and `src/db/`. Anything that must never reach the browser (server actions, `@/db`, modules that query it) starts with `import "server-only"`, so the build fails if a Client Component imports it; Bun stubs that import for tests and scripts (`scripts/server-only.ts`). Code both sides use, like `src/lib/control-rules.ts`, stays free of it.

# Extension compatibility

roam.pub names the exact oldest extension it works with, `EXT_MIN_VERSION` in `src/lib/ext-compat.ts`, on every `/api/ext` response, and older extensions ask people to update; the website's and the extension's majors don't have to match. So `/api/ext` changes are additive: add fields and routes, and branch on `ctx.extVersion` (`extAtLeast` in `src/lib/ext-version.ts`) where a shape has to change. Removing something goes in three steps, announced at `/updates/upcoming` (`src/lib/upcoming.ts`) from the first: the website adds the new shape beside the old one; an extension release moves to it; once `/admin/extension` (or the "Everyone is on extension x" email) shows everyone has updated, the website drops the old shape as its next major, raising `EXT_MIN_VERSION` to that extension version, and moves the entry from upcoming.ts to a `Breaking:` bullet. Production deploys enforce the wait: `bun run db:migrate` (the production pre-deploy step) runs `scripts/ext-gate.ts` first, which fails the deploy while anyone active in the last 30 days is on an extension older than `EXT_MIN_VERSION`. There's no override.
